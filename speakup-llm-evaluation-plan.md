# SpeakUp: LLM-driven evaluation and content — redesign plan

## The number that should drive every decision here

Before any design choice, the free-tier math needs to be on the table, because it changes what "add more LLM reliance" can safely mean.

Groq's free tier publishes limits per model, not one shared pool. `openai/gpt-oss-120b` — the model this app already uses — is capped at 30 requests/minute, 1,000 requests/day, 8,000 tokens/minute, and 200,000 tokens/day, and these limits apply at the organization level, so every signed-in user of this app is drawing against the same 200k-tokens-a-day bucket through the one Edge Function. A second free model, `openai/gpt-oss-20b`, and a third, `llama-3.1-8b-instant`, each have their *own* separate buckets (the 8B model in particular is far more generous: ~14,400 requests/day), because Groq doesn't pool quota across models.

Today's two calls per session (the "Structure" call and the exercise-fit call) run to roughly 1,700 and 1,400 tokens respectively once you count the fixed instructions, the transcript, and the completion — call it ~3,100 tokens/session. Against a 200,000-token daily budget, that's about **64 completed sessions a day, system-wide, before anyone hits the wall** — and that's the *current* design, before adding anything. Requests-per-minute (30) and requests-per-day (1,000) are not the binding constraint; tokens-per-day is, by a wide margin.

That single fact rules out the laziest version of "make the LLM the judge everywhere": bolting a third or fourth call onto every session would drop that ceiling toward 40–50 sessions/day, and a per-session content-generation call would drop it further still. The plan below is built around *not* increasing call count per session, using Groq's separate per-model buckets as real (free) fallback headroom, and keeping anything token-hungry — like growing the content banks — off the per-session request path entirely.

## Design principle: extend the existing two calls, don't add a third

The app already fires exactly two model calls per completed session: the Structure call (`buildCoachingPrompt` in `src/lib/aiCoach.js`) and the exercise-fit call (`buildExerciseFitPrompt`). Both already ask the model to read the transcript and make a judgment call — the Structure call already returns `deliveryNote` and `wordChoiceNote` as free-text asides, and the exercise-fit call already returns a 0–100 `score` for "did they do the assignment." The fix for the "fixed lists gate the real judgment" problem is not a new call — it's promoting what those two calls already return from a secondary note into the primary graded number, and asking each call for a few more structured fields it wasn't asked for before. That's a few hundred extra completion tokens per session, not a new prompt's worth of fixed overhead.

Concretely: `buildCoachingPrompt`'s JSON schema gains `deliveryScore` (0–100), `wordChoiceScore` (0–100), `strongPhrases` (up to 3 verbatim quotes that justify the word-choice score), and `weakPhrases` (up to 3 verbatim quotes that justify it going down) — same verbatim-quote discipline the prompt already enforces for `strongestLine`/`tightenLine`, so this isn't inviting new hallucination risk, just reusing a pattern already proven to work. `buildExerciseFitPrompt` barely changes — it's already the model-first judgment the rest of the app should look more like — except `evidenceQuote` becomes `evidenceQuotes` (array) so the assignment-fit tab has more than one anchor once the fixed-list breakdown under it goes away (see below).

## What happens to the fixed lists

Not everything fixed-list-driven is actually the problem the request describes, so this is file-by-file rather than a blanket removal.

`src/lib/analysis.js` keeps wpm/pace, filler phrase counts, pause count and timing, syllable counting, and `computeArticulationScore` exactly as they are. None of that is list-membership judgment — it's the genuinely objective, recomputable-by-hand math the user explicitly wants kept, and `computeArticulationScore` was never gated on POWER_WORDS/WEAK_WORDS to begin with (it only ever used pace/fillers/pauses/syllables/variety — worth noting since it means the one existing numeric "score" in this file was already clean). The POWER_WORDS/WEAK_WORDS scan and UPGRADE_SUGGESTIONS stay in the file too, but their role changes: they stop being framed as "what strengthened/softened it" — the primary read — and become the always-available, zero-latency fallback content for the Words tab, shown as secondary evidence when the AI call succeeds and promoted to the *only* content shown (with an honest "AI scoring unavailable, here's what a keyword scan caught" framing) when it fails. Free, useful, no longer pretending to be the whole picture.

`src/lib/exerciseEvaluation.js` is the file where the composite scoring math should actually go. `evaluateExplainSimply`'s `plainScore`/`jargonScore`/`relateScore`, `evaluateSnapOpinion`'s `stanceScore`/`supportScore`/`firmnessScore`, and `evaluatePersonalDepth`'s `sensoryScore` are all built by summing hits against JARGON_WORDS, SIMPLIFIER_MARKERS, STANCE_MARKERS, REASONING_MARKERS, CONCESSION_MARKERS, HEDGE_MARKERS, and EMOTION_SENSORY_WORDS — exactly the blind spot described: phrase it differently than the list anticipated and it doesn't register, and two equally good answers score differently by luck of vocabulary. Worth noting these composite numbers were never actually rendered as a headline in `Reflect.jsx`'s `ExerciseFitPanel` in the first place — the model's `aiFeedback.score` from the exercise-fit call already is the headline there — so removing them isn't taking away a number users currently see as authoritative, it's removing a second, quieter, list-gated number sitting in the "ALSO COUNTED AUTOMATICALLY" section that implies more rigor than it has. The underlying `scanWordList` detection stays (jargon words found, stance/hedge phrases found, sensory words found) purely as unscored evidence chips — same demotion pattern as power/weak words above. `evaluateWordOfDay` and `evaluateWordLadder` are untouched: "did the transcript contain this literal target word" is an exact match by design, not a fuzzy list-membership judgment call, and the exercise-fit call already supplements it with the part that needs a model — whether the word was used with its actual meaning, or whether the two words were genuinely connected rather than just both mentioned.

## Fallback and resilience

The app already has the right shape for this — `Reflect.jsx`'s `aiState`/`aiFitState` machine (`idle`/`loading`/`done`/`error`) with a visible retry button and a Save button that only blocks on `loading`, never on `error`, is exactly the "never a broken or blank screen" behavior the redesign needs, and it barely needs new plumbing, just applying to the new score fields the same way it already applies to `aiFeedback.summary`.

What's worth adding: the `ai-feedback` Edge Function currently forwards straight to Groq and returns whatever Groq says, including a 429. Since Groq's rate limits are genuinely separate per model, the Edge Function should catch a 429 from the primary model and retry once against a configured fallback model (`openai/gpt-oss-20b`, or `llama-3.1-8b-instant` for the more generous daily budget) before giving up — that's real, free headroom, not a workaround. The response should include which model actually served the request so the client can log it. This is a small, contained change to `supabase/functions/ai-feedback/index.ts` — no change to the JWT-gated security model. A lighter client-side add: retry-with-jitter on a 429 specifically in `callAiFeedback` (in `aiCoach.js`), so brief contention between concurrent users smooths out before the UI shows an error at all.

I'd explicitly *not* build a proactive request-throttling/queueing layer (e.g., a shared counter table tracking usage before every call) for a first pass — coordinating that correctly across concurrent Edge Function invocations without a dedicated data store is real complexity for a marginal win over "let Groq's 429 be the signal, retry against the fallback model, and degrade to counts-only in the UI if both fail." Worth revisiting only if usage actually gets close to the ~64 sessions/day ceiling above.

## Content banks: the real tradeoff

Two honest options, not a false choice.

Larger static banks, refreshed periodically through an offline batch process, cost almost nothing against the shared quota because generation happens outside the per-session request path entirely — a script or a weekly Supabase Cron job calls the same Groq proxy logic to generate, say, 20–30 new prompts per category at once, checks them against the existing bank for near-duplicates, and appends the ones that pass. Even generous daily batches (a few thousand tokens) are trivial against a 200,000-token budget compared to what per-session generation would cost. The tradeoff is that it's not personalized and not instant — the bank grows over time rather than adapting live to what a given user just said, and someone has to actually look at a batch before merging it if quality matters (or add a second, cheap review pass). Given the roulette already excludes prompts a user has personally already spoken on and saved (`getFreshContentBank`/`topicIdentityKey` in `storage.js`), a meaningfully bigger bank mostly matters for power users who'd otherwise start seeing "exhausted" repeats — which is a real but not urgent problem at current scale.

Fully dynamic per-session generation — call the model to write a fresh prompt at spin time — is the one place in this whole redesign I'd actively avoid, and not because it wouldn't be nice. It adds a third call to a budget that already caps out around 64 sessions/day at two calls; it adds real latency to what's currently an instant, local-array roulette spin (`getContentBank` today does zero network calls); and it removes the ability to review content before a user sees it live, which matters more for open-ended personal/philosophical prompts than for, say, a vocab word. None of that is a "maybe" — it's a straightforward multiplication of the exact constraint the rest of this plan is designed around.

My recommendation is the batch-refresh approach as the default, with one deliberately-opt-in escape hatch: a "spin doesn't feel fresh — generate me a new one" action a user can trigger by hand (not automatic, not on every spin) that fires a single one-off call and, if it looks reasonable, feeds the result back into the shared bank for everyone rather than being a private one-off. That turns an individual user's occasional spend into a shared, permanent asset instead of a repeated cost, which is the right shape for a shared free-tier quota.

## File-by-file summary

`src/lib/aiCoach.js` — extend `buildCoachingPrompt`'s schema with `deliveryScore`, `wordChoiceScore`, `strongPhrases`, `weakPhrases`; extend `parseAiResponse` to read and clamp them; widen `buildExerciseFitPrompt`'s `evidenceQuote` to `evidenceQuotes`; add 429-aware retry-with-jitter in `callAiFeedback`.

`supabase/functions/ai-feedback/index.ts` — catch a 429 from the requested model and retry once against a configured fallback model from a separate Groq quota bucket; return which model actually served the response.

`src/lib/analysis.js` — no change to the objective math; reframe POWER_WORDS/WEAK_WORDS/UPGRADE_SUGGESTIONS as fallback/secondary evidence rather than the primary word-choice read.

`src/lib/exerciseEvaluation.js` — remove the composite `score`/`breakdown` math built from JARGON_WORDS/SIMPLIFIER_MARKERS/STANCE_MARKERS/REASONING_MARKERS/CONCESSION_MARKERS/HEDGE_MARKERS/EMOTION_SENSORY_WORDS; keep the underlying word/phrase detection as unscored evidence chips; leave `evaluateWordOfDay`/`evaluateWordLadder` as-is.

`src/screens/Reflect.jsx` — Words and Delivery tabs get the new AI scores as the headline (score bar, matching how the assignment-fit tab already renders `aiFitFeedback.score`), with the list-scan chips demoted to a secondary "quick scan" section that's promoted back to primary content automatically when `aiState === "error"`; assignment-fit tab drops the scored breakdown rows in favor of plain evidence chips.

`src/lib/content.js` / `src/lib/storage.js` / `supabase/schema.sql` — only if you want the content-bank half now: a new `content_bank` table seeded from today's arrays, `getContentBank`/`getFreshContentBank` reading from it (cached client-side, falling back to the static arrays if the table's empty or unreachable — same fail-open pattern `getFreshContentBank` already uses), plus a small offline generation script or Cron-triggered Edge Function for periodic batch growth. This is genuinely separable from everything above — it touches the schema and the roulette's data path, not the evaluation flow — so it can land as its own phase.

Tests: `analysis.test.js` is unaffected; `exerciseEvaluation.test.js` needs its assertions on removed `score`/`breakdown` fields updated to the new evidence-chip shape; `content.test.js` only changes if the content-bank migration happens.

## Suggested phasing

Phase 1 — the evaluation redesign (`aiCoach.js`, the Edge Function, `analysis.js`, `exerciseEvaluation.js`, `Reflect.jsx`) — is self-contained, doesn't touch the database, and directly answers the core ask: the model becomes the primary judge of delivery and word-choice quality, with objective counts and keyword hits demoted to supporting evidence, at zero added call count and a small, boring 429-fallback safety net.

Phase 2 — the content-bank migration — is optional and separable: bigger blast radius (a new table, a data-migration step, a background generation job), lower urgency (the "already spoken" filter already prevents same-user repeats), and worth doing once phase 1 is live and you have a feel for real usage against the token budget above.
